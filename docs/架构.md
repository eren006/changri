# 长日bot 架构（v2，0.20 起；2026-11-18 按 0.21.8 更新）

给维护的人看：代码放在哪、加功能改哪里、改数据库怎么做、怎么打包发版。玩家怎么装见 [安装指南](安装指南/)。

## 目录

```
长日bot/
  pyproject.toml              包定义；依赖范围（精确版本在 packaging/requirements.lock）
  src/changri/
    __main__.py               命令入口：run / supervise / service / doctor / backup / update / migrate-legacy / version
    VERSION                   版本号（唯一的来源）
    app.py                    组装：NoneBot + 设置平台 + 小手机，run() 开始服务
    paths.py                  PKG_DIR（包）、APP_ROOT（安装目录）、DATA_DIR（数据）——别处不要自己拼 parent.parent
    config.py                 data/config.toml：host / port / log_level（启动前就要知道的几项；其余设置在数据库里）
    core/                     规则和数据：db、roles、rooms、season、messaging、qqsend（往 QQ 发消息）……各功能的业务逻辑
    plugins/<功能>.py         QQ 群里的指令（NoneBot 插件）
    features/<功能>/          每个功能一个文件夹：
        __init__.py             FEATURE = {...}：扩展页卡片、默认开关、设置组、左侧菜单、群指令模块、网址前缀
        admin.py                设置平台页面：register(app, login_required)
        phone.py                小手机页面：register(app, ctx)
      registry.py             收集上面这些，别处不用手写清单
    admin/                    设置平台外壳：登录、首次设置、机器人接入、账号、更新、远程访问、HTTPS、扩展页；common.py 放公用的
    phone/                    小手机外壳：激活码登录、短信礼物、发现页、资料与外观、管理员手机
    storage/                  数据库迁移：migrate.py + migrations/NNNN_*.sql|py
    platform/                 和安装、运行相关：layout（安装目录）、supervisor（看门进程）、service（开机自启）、
                              doctor（自检）、backup、legacy（从老版本搬数据）、remote_media（按需下载的大文件）
    scripts/                  Caddy 安装脚本（一键 HTTPS 用）
    extdocs/                  写扩展的文档和示例（设置平台「扩展」页要读）
    remote_media.json         按需下载的文件清单（背景音乐）
  src/changri_api.py          扩展用的稳定接口（API v1），就是 changri.ext_api
  tests/                      unittest；用 tests/run.py 跑（见「测试」一节），不要直接 unittest discover
  packaging/                  打包：build.py、requirements.lock、changelog.json（每版的更新说明）、
                              windows/、linux/、site/（官网首页、安装页模板）
  tools/                      作者自己用的，不随安装包：release.py（发版流水线）、sync_public.sh / export_public.sh（同步公开仓库）、
                              主页服务器上跑的几个小服务（errors / probe / wishes / console，各有部署说明）
  docs/                       设计文档（这份在这里）
```

为什么群指令不放进 `features/<功能>/`：NoneBot 用模块名的最后一段当插件 ID，都叫 `commands.py` 会重名。所以群指令仍是 `plugins/<功能>.py`，在 FEATURE 的 `module` 里写上。

## 程序会连主页服务器做哪几件事

都只连 system.changri.work，都不带群号、QQ 号、聊天内容（例外：装的人自己在「基础」里填了「联系 QQ」时，报错上报会带上它）：

- **检查更新**（`core/updater.py`）：启动 2 分钟后一次，之后每 6 小时一次，读 `latest.json`。有新版本时后台「更新」亮小红点。
- **匿名使用情况上报**（`core/usage.py`）：跟检查更新一起发；后台「基础」里能关。
- **报错上报**（`core/errlog.py`）：出错后把错误位置和报错文字发过去，密钥一类的字符串先抹掉。
- **外网探测**（`core/netcheck.py`）：管理员在后台点「检查玩家能不能打开」时，请主页服务器回连这台机器的小手机端口。

主页以外，只有一处会连第三方网站：小手机的**每日一句**（`core/dailyquote.py`，默认关，后台「小手机」页开），每天第一次有人打开发现页时，去 v1.hitokoto.cn 和 v2.jinrishici.com 各拉一句，只是一个不带任何信息的 GET。以后再加这类东西也要默认关，并写进 README「安全提醒」。

服务端代码在 `tools/`（errors_service、probe_service、console_service + wishes_service），不随安装包。

## 加一个功能

1. `core/<功能>.py`：规则和数据（不依赖 NoneBot、Flask，方便测试）。
2. `plugins/<功能>.py`：群指令。
3. `features/<功能>/__init__.py`：写 `FEATURE`（照着 `features/precall/__init__.py` 抄）。要在「扩展」页出现、能开关，才需要写。
4. 需要后台页面：`features/<功能>/admin.py` 写 `def register(app, login_required):`，里面照常 `@app.route`。路由名就是函数名，模板里 `url_for("函数名")`。模板放 `admin/templates/`。
5. 需要小手机页面：`features/<功能>/phone.py` 写 `def register(app, ctx):`。`ctx` 里有 `need_login`、`page`、`current`、`_gate`、`_push` 等（见 `phone/app.py` 末尾的 `SimpleNamespace`）。
6. 要新的表或列：见下一节。
7. 测试放 `tests/test_<功能>.py`。

不用改任何清单：registry 会自动找到有 `admin.py` / `phone.py` 的功能。

## 改数据库

- 表结构以 `storage/migrations/` 为准，版本记在每个库的 `PRAGMA user_version`。
- **`0001_baseline.sql` 冻结了，不要改**（测试锁了哈希）。加表、加列：新建 `0002_说明.sql`，编号连续往上；要搬数据就写 `0002_说明.py`，里面 `def up(conn):`（已经在事务里，外键检查关着）。
- 每个库（全局库 + 每个机器人的工作区库）启动时都会自动升到最新；失败整段回滚，下次启动再试。
- 程序比数据库旧（装回了旧版本）会拒绝启动，免得旧代码写坏新库。

## 数据放哪

`DATA_DIR` = 安装目录下的 `data/`（环境变量 `CHANGRI_HOME` 可改）：

```
data/
  config.toml           程序配置（端口等）
  changri.db            全局库：后台账号、机器人清单、全局设置（GLOBAL_CONFIG_PREFIXES 开头的键）
  bots/<AppID>/         每个机器人一个工作区：changri.db、公知二表图片……
  extensions/           用户自己装的扩展
  media/                按需下载的文件（背景音乐）
  backups/              更新前自动备份、手动备份
  .secret_key .setup_code update_pending.json update_failed.txt ……
```

更新永远不碰 `data/`。

## 安装目录和更新

```
<安装目录>/
  runtime/<编号>/       独立 Python + 依赖 + 大媒体文件（字体、大图），在 changri-media/ 下
  versions/<版本>/      程序代码：changri/、changri_api.py、RUNTIME（要用哪个运行环境）
  current               当前版本（一行）
  data/
  启动脚本               Windows：Start-Changri.bat 等；Linux：changri
```

- 启动脚本读 `current` → `versions/<版本>/RUNTIME` → 用对应的 Python 跑 `python -m changri supervise`（看门进程）。
- 看门进程再跑 `python -m changri run`（真正干活的）。子进程退出码 3 = 请重启；`current` 变了 → 看门进程退出码 10 → 启动脚本按新版本重新拉起。
- 在线更新（`core/updater.py`）：下载 → 校验 sha256 + Ed25519 签名 → 解压到 `versions/<新版本>/`（需要时再装新运行环境）→ 备份所有库 → 写 `data/update_pending.json` → 改 `current` → 重启。不覆盖任何正在用的文件。
- 新版本 90 秒内连续退出 3 次：看门进程恢复备份的数据库、`current` 改回旧版本（`updater.rollback_if_failing`）。
- 旧版本留最近 3 个，没人用的运行环境自动删掉。
- 开发时（直接从源码跑）没有这些，`platform.layout.INSTALLED` 为 False，不能在线更新。

## 打包发版

平时用发版流水线（作者自己的电脑上跑，脚本不进公开仓库）：

```bash
# 1. VERSION 改成新版本号，packaging/changelog.json 最上面加这一版的 features / fixes
# 2. 先看一遍会做什么
.venv/bin/python tools/release.py --dry-run
# 3. 正式跑（上传 = 对外发布，要作者明确同意）
.venv/bin/python tools/release.py
# 4. 同步公开仓库：先看差别，作者确认后再推
tools/sync_public.sh
tools/sync_public.sh --push
```

`release.py` 的步骤：preflight（版本号、changelog 有没有这一版、跑全量测试）→ build（调 `packaging/build.py` 出包）→ github（安装包传到 GitHub Release）→ redirect（主页服务器的 `/downloads/`、`/media/` 跳到这一版的 Release 加速镜像）→ site（传 get.sh、安装页、首页，最后传 `latest.json`）→ verify（公开地址逐个核对大小和 sha256）。`--steps verify` 只跑某几步。主页服务器不存安装包，因为它的国际线路太慢。

- **更新说明**写在 `packaging/changelog.json`，每版一条，分 `features`（新功能）和 `fixes`（修 bug）。build.py 把最近 20 条放进 `latest.json` 的 `changes`，后台「更新」页按这两栏列出跳过的所有改动；0.21.6 及更早的版本看的是同时生成的纯文字说明。preflight 发现没有当前版本的条目就停（或者用 `--notes` 给一段文字）。
- 只打包不发布：`.venv/bin/python packaging/build.py --notes "…"`，产出 `release_out/<版本>/site/`，路径和 system.changri.work 上的一样（`latest.json`、`get.sh`、`install.html`、`downloads/`、`media/`）。
- 运行环境编号 = Python 版本 + `requirements.lock` + 大媒体文件 + 精简规则的哈希。不变的话，已安装的机器更新时只下载约 2MB 的代码包。
- 依赖：改 `pyproject.toml` 后，在开发环境装好，再把 `packaging/requirements.lock` 的精确版本对上（`tests/test_lock.py` 会对照开发环境的真实依赖树检查）。只在某个平台需要的包写分号条件（如 `; sys_platform == "win32"`），打包脚本按目标平台判断。
- 签名私钥 `~/.changri_release/private.pem`，必须和 `core/update_pubkey.py` 的公钥配对（脚本会检查）。打包时还会扫一遍程序文件，发现本机口令、用户名、家目录路径、私钥或 .env / .db 文件就停。
- 本机测试：`build.py --platforms macos-arm64 --test-key` 打出临时密钥签名的 Mac 包，可以解压后 `./changri run` 端到端测试安装、更新、回滚。测试包不能上传。
- 换了背景音乐：`build.py --refresh-remote-media` 重新生成 `remote_media.json`。
- Linux 包最低要求 glibc 2.28（Pillow 13 起只有 manylinux_2_28 的包）。
- 公开仓库（github.com/eren006/changri）由 `tools/export_public.sh` 的规则导出：git 忽略的文件、作者专用的工具（release.py、console 等）、PRODUCT.md 和内部设计文档都不进去。不在公开仓库里直接改代码。

## 小手机的端口

所有机器人共用一个端口（全局设置 `phonesrv_port`，默认 5092）。`core/phoneserver.py` 的分发层按请求认机器人：`?b=AppID`（后台发的一次性链接）→ cookie `phone_bot` → 老 cookie `phone_auth_<后6位>` → 在 `/p` 提交的激活码属于谁 → 第一个开着小手机的机器人。认出来以后交给那个机器人自己的小手机应用，在它的工作区里处理。

## 测试

```bash
.venv/bin/python tests/run.py --changed       # 只跑跟改动有关的（相对 main 的提交 + 没提交的改动 + 新文件）
.venv/bin/python tests/run.py --changed --dry # 只列出会跑哪些、为什么
.venv/bin/python tests/run.py storycal play   # 只跑文件名里带这些词的
.venv/bin/python tests/run.py                 # 全量，一个文件一个进程，并行，两分钟左右
.venv/bin/python tests/run.py -j 1 -v         # 不并行、打印每个文件的输出
```

**什么时候跑什么：** 开发时只跑 `--changed`，改完、修完都是它；全量只在发版时跑，`tools/release.py` 的 preflight 会自动跑，跟这次改动无关的地方在那时候兜底（不要加 `--skip-tests`）。

`--changed` 的挑法在 `tests/_affected.py` 开头写着：直接 import 了改动模块的测试；按名字加载的（`nonebot.load_plugin("changri.plugins.x")`、扩展的 `ext:<id>`、页面路径 `/<id>`）；文件名带模块名的；都没有就顺着「谁导入了它」往上找。模板、样式、`.sql` 迁移算它所在的包。改了 `src/` 下的 `.py` 都会顺带跑 `test_static`。只看静态 import，所以会漏掉运行时才连上的关系，这些靠发版时的全量。输出里说「找不到相关测试」的文件，最好补一个测试。

**不要用 `python -m unittest discover`。** `core/db.py` 第一次被导入时就定死了库路径（`CHANGRI_DB_PATH`）。discover 会先把所有测试文件导入一遍，结果大家共用同一个库，一个文件开的开关（比如故事历）会漏到别的文件里，出现「单独跑能过、一起跑就挂」。`tests/run.py` 给每个文件单独开一个进程，还会：

- 把 `PYTHONPATH` 设成本目录的 `src/`：在 git worktree 里用主目录的 `.venv`（装的是主目录那份代码）跑，也测的是这份代码；
- 给每个进程一个新的临时 `CHANGRI_HOME`：测试就算没设对库，也碰不到真的 `data/`。

写新测试：文件开头在导入 changri 之前设 `os.environ["CHANGRI_DB_PATH"] = <临时目录>/t.db`（变量名别写成 `CHANGRI_DB`，以前有 5 个文件写错了，一直写进了开发库）。

几个起检查作用的测试：

- `tests/test_static.py` 用 pyflakes 查「用了没导入的名字」（`pip install -e ".[dev]"` 会装 pyflakes）。
- `tests/test_registry.py` 检查功能声明；`tests/test_migrate.py` 检查迁移；`tests/test_lock.py` 检查依赖锁定。
